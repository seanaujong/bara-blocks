# Problem Statement

Names what's wrong or missing before showing the fix — gives the reader a reason to keep reading
before they've seen any solution. Without it, a walkthrough or guide reads as a list of steps with
no stated point.

In a product walkthrough this is the friction a customer feels; in a developer guide it's the gap
between "installed" and "working"; in a design doc it's the thing required before any option gets
proposed.

> "Checking out a book used to mean waiting in line for the one staffed register, even for a
> single item."
